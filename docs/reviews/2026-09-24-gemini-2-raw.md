### Ranked Verification Findings

#### Finding 1 [P0]: Consecutive API error kill switch is permanently disabled for order placement failures
* **File & Line:** [execution/okx.py:107-118](file:///execution/okx.py#L107-L118) and [ops/session.py:303,339](file:///ops/session.py#L303-L339)
* **What is wrong:** In `execution/okx.py`, `_req()` unconditionally sets `self.errors = 0` whenever an API call succeeds. In `ops/session.py`, `_handle()` calls `acc = broker.account()` before placing each order. If an order placement fails in `broker.place_entry()`, `self.errors` increments to 1. On the next proposed trade, `_handle()` calls `broker.account()`, which succeeds and resets `self.errors` back to 0.
* **Concrete failure scenario:** The exchange rejects order placements due to an invalid contract parameter or post-only restriction. Even if 10 orders fail consecutively, `self.errors` oscillates between 0 and 1 because each failed `place_entry` is preceded by a successful `account()` call. The kill switch threshold of 3 consecutive API errors is never reached, allowing the system to continue submitting failing orders in an unstable state.
* **How to fix:** Track order placement errors separately from read errors, or only reset `self.errors = 0` on successful state-mutating actions (fills/placements), or avoid resetting the error counter inside routine read requests during the signal execution loop.

#### Finding 2 [P0]: Running `--dry-run` locks out live execution for the entire session
* **File & Line:** [ops/session.py:212-214, 239, 323-326](file:///ops/session.py#L212-L326)
* **What is wrong:** In `ops/session.py`, `journal.set("last_signal_time", t_sess.isoformat())` (line 239) runs at the end of step 4 regardless of whether `--dry-run` was supplied.
* **Concrete failure scenario:** The lead runs `python -m ops.session --dry-run` at 07:05 UTC to preview the proposed trade cards. The dry run completes and writes `last_signal_time = "2026-09-24T07:00:00"` to the journal database. Satisfied with the cards, the lead immediately runs `python -m ops.session` at 07:06 UTC to execute real orders. Line 212 checks `journal.get("last_signal_time") == t_sess.isoformat()`, logs `"Signals for the 07:00 UTC session were already handled"`, and exits. All valid signals for that session are permanently lost.
* **How to fix:** Wrap line 239 in a condition so it only sets `last_signal_time` when not running in dry-run mode: `if not args.dry_run: journal.set("last_signal_time", t_sess.isoformat())`.

#### Finding 3 [P0]: Paper broker checks candle history prior to order submission, causing immediate retroactive fills and stop-outs
* **File & Line:** [execution/paper.py:134-137](file:///execution/paper.py#L134-L137) and [execution/paper.py:95-126](file:///execution/paper.py#L95-L126)
* **What is wrong:** When `PaperBroker.place_entry()` records a market or pending order, `checked_to_ms` is set to the current timestamp. However, `_bars_since()` rounds down to the hour start: `start = since_ms - since_ms % 3_600_000`. In `sync()`, the full 1-hour bar containing the placement time is evaluated from minute zero.
* **Concrete failure scenario:** An order is placed at 07:15 UTC. `_bars_since()` fetches the confirmed 07:00 UTC candle covering 07:00 to 08:00. If the asset spiked downwards at 07:05 and recovered before 07:15, the candle's low `l` breached the stop price. In `sync()`, lines 115-119 see `hit_stop = True` on the 07:00 candle and immediately trigger a stop exit at `t["stop"]`, stopping out the trade based on price action that occurred before the trade existed.
* **How to fix:** For paper orders, initialize `checked_to_ms` to the next upcoming candle start (`since_ms - since_ms % 3_600_000 + 3_600_000`) so that past price movements within the entry hour cannot retroactively trigger entries or exits.

#### Finding 4 [P1]: Closed positions API passes an invalid pagination parameter, breaking reconciliation and causing a false kill-switch halt
* **File & Line:** [execution/okx.py:147](file:///execution/okx.py#L147) and [ops/session.py:90-102](file:///ops/session.py#L90-L102)
* **What is wrong:** In `execution/okx.py`, `closed_positions()` calls `/api/v5/account/positions-history` with `{"instType": "FUTURES", "after": str(int(time.time() * 1000))}`. On OKX API v5, `after` is a cursor for `posId` (position ID pagination), not a millisecond timestamp. Passing a timestamp causes either an API error or an empty return list.
* **Concrete failure scenario:** An open position reaches its target and closes on OKX between sessions. At the next session, `pos` no longer contains the position. `reconcile()` queries `broker.closed_positions(since)`. Because `after` contains a timestamp, OKX returns an empty list `[]`. In `ops/session.py`, line 102 triggers: `"position gone from the exchange and no close record found"`. This is added to `problems`, which immediately triggers `halt()`, engaging the kill switch and blocking all future trading until lead review.
* **How to fix:** Remove the `"after"` query parameter from `/api/v5/account/positions-history`. Let OKX return the most recent 100 positions, then filter them by `int(r["uTime"]) >= since_ms` in Python.

#### Finding 5 [P1]: Stage multiplier counts demo trades as live trades, causing real money trades to double risk prematurely
* **File & Line:** [ops/session.py:58-64](file:///ops/session.py#L58-L64)
* **What is wrong:** `stage_mult()` calculates live trade count using `mode != 'paper'`. Because demo trading uses `mode = 'demo'`, demo trades are counted.
* **Concrete failure scenario:** A strategy is tested in demo mode for 30 trades. When the lead approves the strategy for `live_small`, `n` is already 30. Line 63 returns `0.5` instead of `0.25`. The strategy skips its mandatory 30-trade probationary size of 0.25R and risks double the intended risk on real capital from trade 1.
* **How to fix:** In [ops/session.py:62](file:///ops/session.py#L62), filter explicitly for live mode: `n = len(journal.trades("strategy = ? AND mode = 'live' AND status = 'closed'", (strategy,)))`.

#### Finding 6 [P1]: Daily loss calculation adds total unrealized PnL from multi-day trades, triggering false daily halts
* **File & Line:** [ops/session.py:66-70](file:///ops/session.py#L66-L70) and [risk/engine.py:89-90](file:///risk/engine.py#L89-L90)
* **What is wrong:** `pnl_R()` calculates daily PnL by adding the total unrealized PnL (`upl`) of all currently open positions to the closed PnL today. It does not subtract the unrealized PnL that existed at the start of the day.
* **Concrete failure scenario:** A swing position entered three days ago has an open drawdown of -2.5R as of midnight UTC. Today the market is flat and the position loses an additional -0.6R. The daily loss for today is only -0.6R, but `pnl_today_R` calculates `0 + (-3.1R) = -3.1R`. This breaches `daily_loss_stop_R: 3`, halting new trades for the entire day even though the actual loss incurred today was well within limits.
* **How to fix:** Either record start-of-day account equity / start-of-day mark-to-market in the journal, or compute daily PnL as `(equity_now - equity_start_of_day_utc) / one_r`.

#### Finding 7 [P1]: Free margin check in `okx.py` sums raw multi-currency units without currency normalization
* **File & Line:** [execution/okx.py:127-130](file:///execution/okx.py#L127-L130)
* **What is wrong:** In `OkxBroker.account()`, available margin is computed as `avail = sum(float(c.get("availEq") or c.get("availBal") or 0) for c in d.get("details", []))`. The `details` array in OKX balance responses contains individual balances per currency (e.g. BTC, ETH, USDT, EUR).
* **Concrete failure scenario:** An account holds 1.0 BTC (worth $60,000) and 200 USDT. `avail` sums `1.0 + 200 = 201`. When proposing an order requiring $500 of margin, `check()` in `risk/engine.py` rejects the order for `"not enough free margin (500 needed, 201 free)"`, despite the account having tens of thousands of dollars in available equity. Conversely, an account with 10,000 DOGE ($1,500) and 50 USDT computes `avail = 10050`, allowing orders far beyond actual capital.
* **How to fix:** Use the account-level USD margin fields provided by OKX on the root balance object `d`, such as `float(d.get("availEq") or d["totalEq"])`, or filter `details` specifically for the settlement quote currency (e.g. USDT) of the X-Perp contracts.

#### Finding 8 [P1]: Housekeeping unconditionally cancels all pending limit orders after one session, ignoring strategy expiries
* **File & Line:** [ops/session.py:194-197](file:///ops/session.py#L194-L197) and [harness/engine.py:72](file:///harness/engine.py#L72)
* **What is wrong:** In `ops/session.py`, line 194 cancels any pending order where `placed_at < session_time(t_now)`. This forces all limit orders to expire at the very next session (~12 hours). However, the backtest engine (`harness/engine.py:72`) supports multi-session and multi-day expiries (`sig.entry.expiry`).
* **Concrete failure scenario:** A strategy generates limit entries with an expiry of 48 hours. In the backtest, limit orders wait up to 4 sessions to fill. In live and paper trading, the order is cancelled after 1 session. Backtest fill rates and live fill rates diverge significantly.
* **How to fix:** Store `sig.entry.expiry` (in hours) in the `trades` database table upon creation, and only cancel pending orders in housekeeping when `placed_at + expiry_h <= t_now`.

#### Finding 9 [P1]: BTC-beta calculation formula differs between backtest and live risk engine
* **File & Line:** [harness/engine.py:151-164](file:///harness/engine.py#L151-L164) vs [ops/live_data.py:79-89](file:///ops/live_data.py#L79-L89)
* **What is wrong:** `harness/engine.py` bins hourly returns by UTC day and shifts by one full day (`.shift(1)`), meaning backtest beta is held constant during day D using data through day D-1. In contrast, `ops/live_data.py`
...computes rolling beta dynamically over the preceding 30 days up to the exact session timestamp `now`, without daily binning or day-shifting.
* **Concrete failure scenario:** A strategy signal near the 3.0R direction limit passes in backtest because yesterday's beta was 0.95. In live trading, today's intraday returns pushed beta to 1.05, pushing exposure to 3.05R and causing the live risk engine to veto the trade. Backtest and live execution diverge.
* **How to fix:** Unify the two implementations into a single shared function that calculates beta identically for both backtest and live sessions.

#### Finding 10 [P1]: Gatekeeper allows aborted or interrupted holdout runs to be re-run
* **File & Line:** [harness/gatekeeper.py:41-43, 67, 75](file:///harness/gatekeeper.py#L41-L75)
* **What is wrong:** Line 67 records `{"kind": "holdout_start", ...}` in the registry before backtest execution. However, `preconditions()` line 41 only checks `any(e["kind"] == "holdout" for e in entries)`. If a holdout execution crashes, times out, or is cancelled before line 75, no record with `kind: "holdout"` exists.
* **Concrete failure scenario:** A holdout evaluation begins and prints intermediate results to stdout. Seeing poor performance or encountering an error, the operator interrupts the process. Because only `holdout_start` was recorded, `preconditions()` permits running gatekeeper again on the same hypothesis with tweaked parameters, violating the strict single-holdout rule.
* **How to fix:** In [harness/gatekeeper.py:41](file:///harness/gatekeeper.py#L41), block execution if either entry exists: `if any(e["hypothesis"] == hyp and e["kind"] in ("holdout", "holdout_start") for e in entries): raise Refused(...)`.

#### Finding 11 [P1]: Target exits on OKX are almost always recorded as "other" in the trade journal
* **File & Line:** [ops/session.py:94-98](file:///ops/session.py#L94-L98)
* **What is wrong:** In `reconcile()`, the exit reason check `reason = "target" if s * (c["close_px"] - t["target"]) >= 0 else ...` assumes the fill price will be at or beyond the target. Attached take-profit orders on OKX execute as market orders on trigger (`tpOrdPx: "-1"`), filling at the bid (for longs) or ask (for shorts).
* **Concrete failure scenario:** A long position hits its target price of 100.0. The market sell order fills at 99.98 after crossing the spread. Because `1 * (99.98 - 100.0) = -0.02 < 0`, `s * (close_px - target) >= 0` evaluates to False. It is also above the stop, so the journal records the exit as `"other"`. Strategy journal statistics and target win rates are systematically corrupted.
* **How to fix:** Determine exit reason using OKX algo order history, or check proximity to target versus stop: `reason = "target" if abs(c["close_px"] - t["target"]) < abs(c["close_px"] - t["stop"]) else "stop"`.

#### Finding 12 [P2]: Duplicate primary key in journal on re-running a session crashes the script
* **File & Line:** [ops/session.py:333-337](file:///ops/session.py#L333-L337) and [ops/journal.py:50-54](file:///ops/journal.py#L50-L54)
* **What is wrong:** `cl` is derived deterministically from strategy ID, coin, and session timestamp. `journal.add_trade()` performs a raw `INSERT INTO trades`, where `id` is the primary key.
* **Concrete failure scenario:** An order is inserted into the journal, but the process crashes during placement or user prompt. When the lead restarts the session, `journal.add_trade()` attempts to insert the same `cl` again, raising an unhandled `sqlite3.IntegrityError: UNIQUE constraint failed: trades.id` and crashing the session.
* **How to fix:** Use `INSERT OR REPLACE INTO trades` in `add_trade()`, or append a short random salt/attempt suffix to `cl`.

#### Finding 13 [P2]: Contract size string formatting can produce invalid floating-point strings
* **File & Line:** [execution/okx.py:158](file:///execution/okx.py#L158) and [risk/engine.py:99-100](file:///risk/engine.py#L99-L100)
* **What is wrong:** `contracts = lots * p.lot_sz`. Floating point arithmetic can yield numbers like `12.300000000000002`. Line 158 formats this as `"sz": str(contracts)`.
* **Concrete failure scenario:** An instrument with fractional `lot_sz` of 0.1 computes 123 lots as `12.300000000000002`. OKX rejects the order with an invalid size parameter error.
* **How to fix:** Quantize `contracts` to the contract lot size decimal precision using `Decimal` before converting to string, similar to `round_px()`.

#### Finding 14 [P2]: Uncaught `OkxError` in `close()` crashes housekeeping
* **File & Line:** [execution/okx.py:169-177](file:///execution/okx.py#L169-L177) and [ops/session.py:199](file:///ops/session.py#L199)
* **What is wrong:** In `okx.close()`, `cancel-algos` is called after `close-position(autoCxl=True)`. Because `autoCxl=True` already tells OKX to cancel attached algo orders, a subsequent call to `cancel-algos` can return error code 51401 (order not found). This raises an `OkxError`, which is unhandled in `ops/session.py:199`.
* **Concrete failure scenario:** A position hits its time limit and housekeeping calls `b.close()`. The call raises `OkxError`. Step 3 crashes, preventing Step 4 (signals and new orders) and the session report from executing.
* **How to fix:** Wrap the `cancel-algos` call in a `try...except OkxError` block inside `close()`, or catch exceptions during time-exit processing in `session.py`.

#### Finding 15 [P2]: Capital withdrawal triggers false drawdown halt kill-switch
* **File & Line:** [ops/session.py:174-175](file:///ops/session.py#L174-L175) and [risk/engine.py:78](file:///risk/engine.py#L78)
* **What is wrong:** Peak equity is tracked purely as nominal account equity (`peak_live`). The system does not track deposits or withdrawals.
* **Concrete failure scenario:** An account grows to $15,000 equity (peak = $15,000). The lead withdraws $2,000 profits, leaving $13,000. Sizing 1R is $75. The drawdown calculation sees $(15000 - 13000) / 75 = 26.7R \ge 20R$. A false drawdown halt is immediately triggered, locking the account until manual review.
* **How to fix:** Track capital cash flows in the journal to adjust the nominal peak equity downward when withdrawals occur, or track drawdown using unitized NAV.

#### Finding 16 [P2]: `xperp_instruments()` overwrites coin specifications when multiple quote currencies exist
* **File & Line:** [execution/okx.py:46](file:///execution/okx.py#L46)
* **What is wrong:** `out[i["instFamily"].split("-")[0]] = ...` keys instruments strictly by base coin. In the EEA, OKX frequently lists both EUR-margined and USDT-margined X-Perps for major coins like BTC and ETH.

#### Finding 17 [P2]: No cryptographic authentication on `--resume` or kill switch clearing
* **File & Line:** [ops/session.py:143-154](file:///ops/session.py#L143-L154) and [config/limits.yaml:2-3](file:///config/limits.yaml#L2-L3)
* **What is wrong:** Rule 7 states agents may never resume trading. However, `--resume` simply reads plain text from standard input: `input("Type RESUME to clear the halt: ")`.
* **Concrete failure scenario:** An autonomous subagent or compromised background script runs `echo "RESUME\nOperator review" | python -m ops.session --resume`, clearing a critical risk halt without actual lead intervention.
* **How to fix:** Require a private key signature, passphrase verified against an environment variable known only to the lead, or a physical verification token to clear halts.

#### Finding 18 [P3]: Margin check omits taker fees to open
* **File & Line:** [risk/engine.py:120-121](file:///risk/engine.py#L120-L121)
* **What is wrong:** `margin = notional / lev`. OKX isolated margin checks that available balance covers initial margin plus the opening taker fee.
* **Concrete failure scenario:** If free margin is barely equal to `margin`, OKX rejects the order with an insufficient balance error.
* **How to fix:** Add estimated taker fees to the required margin check: `margin = (notional / lev) + (notional * p.mmr)`.

### Verdict

This codebase is **not safe to run in live mode** and will experience operational disruptions even in paper and demo modes. Paper mode suffers from immediate retroactive candle fills in `_bars_since()` (Finding 3), while demo mode will trigger false kill-switch halts due to broken position-history pagination (Finding 4) and corrupted multi-currency margin summation (Finding 7). Furthermore, testing with `--dry-run` locks out subsequent trading runs for that session (Finding 2), and order placement failures fail to register on the consecutive error counter (Finding 1). Before live mode is enabled, the team must fix the order error counter, repair position reconciliation pagination, adjust available margin calculation to account currency units, isolate dry runs from session state, correct the stage multiplier live mode filter, and establish authenticated controls for clearing halts.
